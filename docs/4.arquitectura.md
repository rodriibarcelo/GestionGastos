# 4. Arquitectura y decisiones de diseño

## 4.1. Enfoque arquitectónico

La aplicación sigue un esquema **en capas**, alineado con las prácticas de la asignatura:

- **Lanzador (JavaFX)** (`gestiongastos.lanzador.GestionGastosApp`): punto de arranque de la aplicación, muestra `VistaLogin` y, tras autenticación, carga `VistaMain`.
- **Vista (JavaFX)** (`gestiongastos.vista`): pantallas, formularios y componentes UI.
- **Controlador** (`gestiongastos.controlador.Controlador`): punto de entrada de casos de uso, mantiene el **usuario autenticado** y coordina servicios.
- **Servicios de aplicación** (`gestiongastos.servicio`): lógica de negocio (CRUD, filtros, totales, cuentas compartidas).
- **Persistencia** (`gestiongastos.persistencia`): contratos *Repository* e implementación JSON.
- **Dominio** (`gestiongastos.dominio`): entidades del problema (Gasto, Categoria, CuentaCompartida, etc.).
- **Infraestructura adicional**:
  - **Alertas** (`gestiongastos.alertas`): evaluación de límites mediante estrategia.
  - **Importador** (`gestiongastos.importador`): importación extensible de ficheros, adaptador + método factoria.
  - **CLI** (`gestiongastos.cli`): entrada alternativa por consola.

### Dirección de dependencias
Las capas superiores dependen de las inferiores (Vista → Controlador → Servicios → Repositorios/Dominio).  
Los **servicios** trabajan contra **interfaces** de repositorio, mientras que el **Controlador centraliza el cableado** usando las implementaciones JSON (`*RepositoryJson`, en varios casos mediante `getInstance()`), manteniendo al margen la lógica de aplicación de los detalles de persistencia.

## 4.2. Persistencia en JSON (Jackson)

La información se almacena en `data/*.json`. La persistencia se apoya en `JsonStorage`, que encapsula Jackson.  
Para simplificar la serialización:

- Las asociaciones entre entidades se representan por **UUID** (por ejemplo, `Gasto.categoriaId`).
- Los repositorios mantienen una **colección en memoria** y, tras operaciones de modificación, realizan el volcado completo al fichero correspondiente `saveList(...)` (p. ej., `gastos.json`, `notificaciones.json`).

## 4.3. Visualización: CalendarFX

Para cumplir el enunciado, se integra **CalendarFX** en `VistaCalendario`, creando entradas (`Entry`) a partir de los gastos y mostrándolas en vistas de calendario.

## 4.4. Decisiones relevantes

- **UUID como clave primaria** en el dominio: facilita identificación y persistencia sin base de datos.
- **Precisión en datos del dominio**: importes con `BigDecimal`; fecha de gasto con `LocalDate`, marca temporal de notificación con `LocalDateTime`.
- **Servicios con operaciones expresivas**: `ServicioGastos.filtrar(...)` permite combinar criterios (fechas/categoría) y se reutiliza para cálculos agregados (`total`).
- **Ámbito del usuario autenticado**: el `Controlador` mantiene el **usuario actual** y aplica el filtrado por `usuarioId` en listados/histórico, manteniendo repositorios y dominio independientes del concepto de “sesión”.
- **Cuentas compartidas con saldo por participante**: el cálculo se centraliza en `CuentaCompartida.registrarGasto(...)`, evitando duplicación de lógica.
- **Historial de notificaciones**: se persiste en JSON (`NotificacionRepositoryJson`) y se consulta desde la aplicación cuando el usuario lo requiere.

Resumen: arquitectura en capas con controlador como coordinador y persistencia JSON encapsulada (JsonStorage + repositorios), manteniendo el dominio simple y trazable mediante UUID.
